# HANDOFF — рабочая память проекта Quiz Party

Файл для того, чтобы **не наступать второй раз на те же грабли**. Здесь не
описание архитектуры «вообще», а конкретные правила и ловушки, на которых мы
уже обожглись. Каждый пункт — это чья-то потерянная вечеринка или час отладки.

**Кто правит:** тот, кто вносит изменение, обновляет этот файл в том же
коммите. Устаревший HANDOFF хуже отсутствующего — ему верят.

Последняя сверка: версия **8.38**.

---

## 1. Деплой

Прод — это **папка `docs/`**. GitHub Pages раздаёт её, больше ничего.

Отсюда главное следствие: **пуш в `src/` не деплоит.** Можно спокойно
копить правки в репозитории неделю, сайт останется на прежней версии.
Прод меняется только когда пересобрана `docs/`.

Два способа собрать:

| способ | когда |
|---|---|
| `./deploy.sh` | ты в Codespaces и правишь код локально |
| Actions → **deploy** → Run workflow | ничего открывать не хочется, сборка на серверах GitHub |

Оба гоняют `tsc`, **линтер**, тесты и сборку до того, как трогают `docs/`.
Красный шаг — деплоя нет, прод живёт на старом бандле.

**Ловушка:** после запуска workflow коммит с новой `docs/` создаётся **на
сервере**. Первое, что делаешь в Codespaces — `git pull`, иначе локальная
копия отстанет и `deploy.sh` упрётся в конфликт.

### Секреты

`VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` лежат в Settings → Secrets and
variables → Actions. Вшиваются в бандл на этапе сборки.

**Ловушка, которая уже стоила одного сломанного прода:** в `VITE_SUPABASE_URL`
**не должно быть слэша в конце**. Со слэшем адрес запроса склеивается в
двойной `//`, и Supabase отвечает `Invalid path specified in request URL` —
вход в редактор просто перестаёт работать. Правильно: `https://…supabase.co`

### Версия

`src/version.ts` бампаем **в каждой правке**. Номер виден в углу экранов, и
`deploy.sh` отдельно проверяет, что версия из исходников попала в сборку.
Если на проде номер старый — деплой прошёл не из того дерева, и обсуждать
правки рано.

## 1a. Бандл: по файлу на экран (с 8.38)

Раньше сборка была одним куском на 648 КБ: гость, открывший `#/player`,
качал вместе со своим экраном проектор, админку и редактор пакетов. Теперь
экраны грузятся отдельными файлами (`React.lazy` в `src/App.tsx`).

Что кто качает после разреза (JS, без CSS):

| экран | было | стало |
|---|---|---|
| телефон игрока | 648 КБ | **423 КБ** |
| админка | 648 КБ | 441 КБ |
| проектор | 648 КБ | 499 КБ |
| редактор | 648 КБ | 492 КБ |

Остаток — библиотеки (React, роутер, клиент Supabase): 377 КБ одним файлом
`vendor`, делить их нечем. Зато он не меняется между версиями, и браузер,
уже заходивший на сайт, после деплоя тянет только наш код.

**Три вещи, которые в этом разрезе легко сломать:**

- **Импорт из `HostScreen.tsx` тянет весь проектор.** Именно поэтому
  `mediaUrl` и `lenClass` переехали в `src/lib/media.ts`: пока редактор
  импортировал их из проектора, его чанк утаскивал 2400 строк HostScreen
  целиком, и разрез не давал ничего. Нужна общая мелочь — клади в `lib/`,
  а не экспортируй из экрана.
- **Первый заход на экран — это запрос в сеть.** Чтобы переход
  «проектор → админка» не зависел от связи в ту секунду, остальные экраны
  ведущего подтягиваются заранее, в простое (`Prefetch` в `App.tsx`).
  Игроку чужие экраны не тянем: у него узкий канал.
- **Файл экрана может не доехать** — сеть моргнула или прод пересобрали,
  пока вкладка висела открытой (имена файлов содержат хэш, старые при
  деплое исчезают). На этот случай в `App.tsx` есть `ChunkBoundary`:
  показывает понятный текст с кнопкой вместо белого экрана и один раз
  пробует перезагрузиться сам.

**Ловушка изнутри `ChunkBoundary`:** вызов `location.reload()` прямо в
`componentDidCatch` оставлял белый экран — React не успевал отрисовать
сообщение. Перезагрузка отложена на 1.5 секунды: сначала человек видит
текст, потом страница пробует подняться.

## 2. Стили: раскладка по темам

**Правило:** правки складываются в файл СВОЕЙ темы, а не в конец сборки.
Файл-свалка «на всё подряд» запрещён — именно из-за него мёртвые правила
живут годами и выглядят рабочими.

| файл | зона ответственности |
|---|---|
| `01-base.css` | переменные, типографика, базовые классы |
| `03/05` | тема НГ, сосульки |
| `14-theme-potter.css` | тема ГП |
| `28-theme-cyber.css` | тема киберпанк: таймер, рамка вопроса |
| `07-editor.css` | редактор |
| `22-question.css` | экран вопроса: медиа, варианты, масштаб картинок |
| `23-answers.css` | экран разбора: ответ, появление, картинки |
| `24-round-intro.css` | заставка раунда |
| `25-results.css` / `26-admin.css` / `27-lobby.css` | итоги / админка / лобби |

**Порядок `@import` в `global.css` — это каскад, а не список.** Кто ниже, тот
перебивает. `28-theme-cyber.css` обязан идти **после** `26-admin.css`: там
лежит базовое кольцо таймера, которое он дополняет. Не переставляй импорты
«для порядка».

### Долг, который стоит разгрести

- **61 класс из 485** описан в CSS, но не встречается в разметке. Часть —
  ложные срабатывания (имена, собираемые в шаблонных строках), но часть
  настоящая: например, все правила `.answers-screen` (24 строки) не работают
  вообще — такого класса в разметке нет. Из-за этого баг с наложением
  картинки на текст прожил долго: «правило есть, значит должно работать».
- `18-patch-745.css` и `19-patch-746.css` — свалки по номерам задач, а не по
  темам. Разнести по зонам ответственности.
- Восемь `!important` в `23-answers.css` — признак войны каскадов.

**Ловушка (закрыта в 8.38):** vitest подхватывал только файлы вида

стоит — файл можно и вовсе забыть добавить в git.

### Линтер (с 8.38)

`npx eslint .` или `npm run lint`. Конфиг — `eslint.config.js`, узкий
намеренно: главная его задача — правило `react-hooks/rules-of-hooks`,
которое ловит **хук после раннего `return`** (падение React #310, видное
только в рантайме: ни типы, ни тесты его не находят).

Первый же прогон нашёл два таких места, оба живые:

- `AnswerForm` в `PlayerPage.tsx` — при скрытии последнего вопроса раунда
  набор хуков менялся между рендерами, то есть падение на телефоне игрока;
- `MelodyBoard` в `MelodyRound.tsx` — то же самое на проекторе в момент,
  когда темы приезжают из пакета и заглушка сменяется доской.

Оба починены переносом: ранний выход — только ниже всех хуков.

Красным линтер становится **только на ошибках**. Предупреждений про
зависимости эффектов около тридцати, они осознанные (полный список
зависимостей крутил бы эффект каждый кадр) и деплою не мешают. Добавляешь
правило — сразу чини найденное, иначе `npm run lint` станет красным
навсегда и его перестанут читать.

Юнит-тесты не ловят вёрстку. Все наложения элементов находились только
рендером в браузере.

## 3a. Фазы игры

`lobby → round_intro → question → [recap] → answer_time → show_answers →
[scoreboard] → [break] → next / finale`

- **`recap`** — повтор всех вопросов слайдами. Включается галочкой
  «повторить вопросы слайдами» (`settings.recap_before_answers`), работает
  только при `answers_reveal === 'after_round'`. Слайд держится 5 секунд
  ИЛИ пока играет озвучка вопроса — что дольше.
- Маршрут после раунда считает ТОЛЬКО `afterRoundStep` из `src/lib/flow.ts`.
  Своих копий этой логики быть не должно: кнопка «Завершить раунд» на
  проекторе однажды прыгала в следующий раунд напрямую, и настроенные
  табло с перерывом молча пропускались — после мелодии и «Своей игры»
  табло не показывалось, хотя галочка стояла.

## 3b. Репетиция и сверка баллов (?dev=1)

`src/lib/devSeed.ts` + панель внизу админки. Видна ТОЛЬКО когда в адресе есть
`dev=1` — на боевой игре её не существует.

- **+ ДЕМО-КОМАНДЫ** — заводит «Тест-1/2/3» в текущей игре.
- **ЗАПОЛНИТЬ РАУНД** — генерит ответы под формат каждого вопроса
  (`answer.mode`), с перекосом ~65% в сторону верного, чтобы проверялись обе
  ветки. Ставки — по правилам механики. Upsert: повторный запуск
  перезаписывает, дублей нет. Трогает только демо-команды.
- **СВЕРИТЬ БАЛЛЫ** — считает ожидаемую сумму НЕЗАВИСИМО от `totals.ts`,
  по правилам механики словами, и показывает «ждали / вышло / Δ».
- **УДАЛИТЬ ДЕМО** — на случай нескольких прогонов подряд. Полный сброс игры
  (`resetGameHard`) и так уносит демо-данные: они пишутся с текущим
  `game_id`, как обычные.

**Независимость расчёта — не формальность.** Первая версия сверки считала
«балл за верный ответ» для всех механик, и тесты сразу показали расхождение:
у спринта два балла за вопрос плюс бонус за полный ответ, у уникальных
ставок к верной добавляется единица, а неверная вычитается. Если срисовать
формулу с кода подсчёта, сверка перестанет что-либо проверять.

- Индекс слайда хранится в `question_index` сессии (как шаг финала).

## 4. Подсчёт баллов

Вся логика — `src/lib/totals.ts`. Две функции: `computeTotals` (сумма) и
`computeRoundScores` (колонки табло). **Правя одну, правь вторую**, иначе
строка на табло не сходится сама с собой.

Правила по механикам:

- **Своя игра (`jeopardy`)**: балл = **цена плитки**. Ни скорость ответа, ни
  ставки не влияют. Порядок ответов в модалке нужен ведущему глазами и в
  баллы не идёт. Засчитывается только явная оценка ведущего `is_correct ===
  true`; неоценённый ответ даёт 0.
- **Мелодия**: сумма `stake` у верных.
- **`thematic_x2`**: удвоение финального вопроса — есть в обеих функциях.
- **Бумажный балл** (`q-paper-*`) перебивает автоподсчёт.

**Ловушка родом из архитектуры (закрыта в 8.38).** Ответы «Своей игры»
лежали по ключу `q-t<плитка>`, а уникальность в БД — по паре
`(team_id, question_ref)`. Номера раунда в ключе не было: пока раунд «Своя
игра» один, всё сходилось, но два таких раунда в одном паке начали бы
молча перетирать ответы друг друга.

Теперь ключ — `q-t<раунд>-<плитка>`, а разбор обеих форм лежит в
**`src/lib/jeopardyRef.ts`**. Старый формат читается по-прежнему: игры,
сыгранные до 8.38, свои ответы не теряют.

Ключ трогают четыре места, и все ходят через этот модуль: запись на
телефоне (`PlayerPage`), чтение в модалке плитки (`HostScreen`), подсчёт
(`totals.ts`) и репетиция (`devSeed.ts`). **Сверка баллов разбирает ключ
своим выражением намеренно** — она обязана оставаться независимой от кода
подсчёта.

## 5. Картинки

- `max-height: 100%` у картинки работает, **только если у контейнера
  определённая высота** (`flex: 1 1 0` или заданный `max-height`). Иначе
  процент не разрешается и картинка уходит в свой натуральный размер —
  так она и наползала на текст вопроса.
- У контейнера медиа есть **и пол, и потолок**. Потолок не даёт задавить
  текст, пол не даёт картинке схлопнуться в марку 70px, когда сверху длинный
  вопрос, а снизу варианты.
- **`media.scale`** (поле вопроса, проценты) меняет размер **на экране**, не
  трогая файл. Диапазон **50…100** и это проверенный предел, а не
  осторожность: картинка и так занимает всё свободное место, поэтому больше
  100% физически ничего не меняет.
- **`.eq-row`** — ряд картинок, выровненный по высоте. Ширину каждой ячейке
  задаёт её собственная пропорция (`flex-grow` из JSX по `naturalWidth /
  naturalHeight`). Включается автоматически при двух и более картинках.
- Загрузка уже сама ужимает до 1920px по длинной стороне и жмёт в JPEG 85%
  (`src/lib/imageCompress.ts`). Отдельный «редактор размеров» не нужен.
- **Медиа следующего вопроса предзагружается** (`usePreloadNext`): пока зал
  смотрит текущий вопрос, браузер тихо тянет картинки, озвучку и видео
  следующего. Ровно на один вопрос вперёд — тянуть весь пак значит забить
  канал тогда, когда он нужен текущему вопросу.

### Медиа из репозитория вместо Supabase

`mediaUrl` пропускает абсолютные ссылки как есть: всё, что начинается с
`http`, уходит без изменений. Значит файл можно держать не в хранилище.

**Но класть его надо в `public/`, а НЕ в `docs/`.** `docs/` пересобирается
при каждом деплое (`rm -rf docs && cp -r dist docs`) — файл оттуда пропадёт.
Vite копирует `public/` в сборку автоматически.

Порядок: положить файл в `public/`, задеплоить, получить адрес
`https://akwunavi.github.io/quiz-party/<имя файла>` и вставить его в слот
медиа кнопкой **«+ вставить ссылку»** (появляется рядом с выбором файла).

Уже лежат: `main.mp3`, `lobby_2.mp3`, `final.mp3` — адреса вида
`https://akwunavi.github.io/quiz-party/lobby_2.mp3`.

Вложенные папки работают так же: `public/media/x.mp3` → адрес
`.../quiz-party/media/x.mp3`.

Ограничение GitHub: файл до 100 МБ, весь репозиторий разумно держать под
1 ГБ. Для фоновой музыки этого с запасом.

## 6. Как проверять вёрстку

Юнит-тестами наложения не ловятся. Проверка — рендер реальной разметки на
собранном CSS в headless-браузере и замер координат: пересекаются ли рамки
элементов, не уехал ли контент под кнопки или под таймер.

**Проверять в ДВУХ режимах игры.** `play_mode` бывает `online` (с
телефонами) и `paper` (без телефонов), и у бумажного своя вёрстка: нет
колонки «ответы команд», нет QR, у лобби свои правила размеров. На этом уже
обожглись: правило `paper-lobby` задавало размер строкам логотипа отдельно и
перебивало общую формулу — буквы рендерились в 145px, а межстрочный интервал
брался от 234px, между QUIZ и PARTY зияла дыра. В обычном режиме всё
выглядело правильно.

Что проверять при любой правке экранов, **по всем трём темам и обоим
режимам игры**:

- вопрос: с картинкой и без, с вариантами и без, длинный текст и короткий
- варианты: длинные формулировки (не налезают ли на кнопки)
- разбор: до показа ответа и после, с картинкой и без, с подсказкой и без
- несколько картинок: 2, 3, 4 — и разной пропорции
- ширины 1280 / 1600 / 1920

Известные точки столкновения: рамка вопроса и кольцо таймера сверху; сетка
вариантов и кнопки «Назад / Далее» снизу; текст вопроса и картинка между
собой.

**Ловушка самого стенда.** В headless-браузере `location.reload()`, вызванный
из кода страницы, оставляет её висеть в состоянии загрузки: белый экран, ноль
ошибок в консоли. К приложению это отношения не имеет — проверено на сборке
из `main`, где никакого разреза бандла ещё нет. Если такое увидел, сверься с
эталоном, прежде чем чинить несуществующий баг.

## 6a. Блиц: состояние вердикта

Три правила, каждое стоило отдельного разбора после первой живой прогонки.

**Вердикт снимается вместе с попыткой.** `answerWrong` при оставшихся
попытках обязан ставить `verdict: undefined`. Пока он этого не делал, на
проекторе навсегда висело «НЕВЕРНО», у ведущего вместо «Скип −1» торчала
кнопка «Исправить», а телефон не понимал, что можно отвечать снова.
Кнопки, завязанные на `!cur.verdict`, из-за этого исчезали после первой
ошибки. Правильное условие для «ещё можно ходить» — `cur.verdict !== 'ok'`.

**Форма ответа появляется вместе с вопросом.** Между ходами `current`
пуст пять секунд (`NEXT_DELAY_MS`). Всё это время команда, чей ход,
смотрела на пустое поле и многоточие — казалось, что телефон завис.
Экран игрока обязан различать «мой ход, вопрос ещё не выехал» и «мой ход,
вопрос на экране».

**Отсчёт окна на исправление — от `pausedAt`, не от последнего ответа.**
Таймер команды стоит, пока идёт проверка. Если пересоздавать пятисекундное
окно на каждую правку, команда держит своё время остановленным сколько
угодно, отправляя новый вариант каждые четыре секунды.

## 7. Пул доработок на будущее

Не срочно, но записано, чтобы не потерялось.

### ⚠ ДОСТУП К ДАННЫМ (после ближайшей игры)

Проверено 26.08.2026. RLS включён на всех 12 таблицах, но политики
складываются по «или»: достаточно одной разрешающей. Такие есть.

- **`pack_questions`** — политика `quest_read` с условием `true`. Любой
  участник вытягивает из консоли **весь пак с правильными ответами** до
  того, как их зададут. Для викторины это худшая из дыр.
- **`game_state`** — две политики на UPDATE: `gs_update` (требует
  редактора) и `gs_write` (`true`). Побеждает вторая: игрок может
  переключить фазу, сменить вопрос, показать ответ залу.
- **`answers`** — UPDATE и DELETE с `true`. Можно проставить себе
  `is_correct` или удалить чужие ответы.
- **`packs`** — `packs_anon_status` разрешает UPDATE **любой** колонки
  любому. Задумывалась под смену статуса, ограничения по колонкам нет.
- **`teams`** — INSERT/UPDATE/DELETE открыты.

Причина общая: поверх старых строгих политик доклеили разрешающие, старые
не убрали. Дубликаты видны почти на каждой таблице.

Сложность в том, что игроки анонимные: просто «запретить анониму писать»
нельзя, он должен вносить свой ответ. Правильное лечение — перевести запись
на функции с проверкой на стороне базы (игрок пишет только за свою команду и
только в текущий вопрос, `is_correct` анониму недоступен). Это затрагивает и
клиент. Быстрый промежуточный шаг — убрать дубликаты, закрыть чтение
`pack_questions`, убрать `gs_write`, снять UPDATE/DELETE на `answers`;
предварительно убедиться, что ведущий работает под авторизованной сессией.

**Решение от 26.08.2026: не трогаем до следующей игры.** Менять доступы
перед боевым прогоном — риск сломать то, что работает.
