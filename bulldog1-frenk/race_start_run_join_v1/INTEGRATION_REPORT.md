# Можно ли внедрить f35 → #88 в Race Scenario V3 без изменения результатов (14.10.2026)
Только чтение и расчёт. V3 (`dog4-v3-lab`), физика гонки, RUN, оригиналы и production не менялись, merge/deploy нет. Скрипт: `integration_check/check.mjs` (импортирует `model.mjs` и `layout.json` только для чтения), результаты: `integration_check/check_results.json`.

## Короткий вывод
**Да, можно, и результаты гонки при этом не меняются, но только при одном условии: длительность физического разгона (velocityRamp) остаётся прежней, 31 кадр = 1,2917 с, и в метаданных клипа отделяется от кадра визуального стыка с RUN.** При такой развязке движок бит-в-бит тот же (максимальная разница прогресса 0), а визуально меняются ровно два кадра окна START. Если связать конец разгона с визуальным стыком (как в моём первом preview), разгон сократится на 2 кадра, и результаты Френка изменятся (раньше на 0,042 с за каждый START).

## 1. Как длительность RACE_START связана с движением
- **V3 сегодня:** физика задана константами `model.mjs`: `START=1` с, `STOP=37/24`, `RUN_JOIN=23/24`, цикл RUN 0,5 с. Прогресс в START: `p0 + v·START/2·2·(u³ − u⁴/2)`, скорость `v·smooth(u)`. Кадр клипа выбирается чистой функцией времени `frameFor()` (для №4 START: 40 кадров на 1 с, 24 кадра по 72 fps и 16 по 24 fps). Победитель определяется аналитическим `crossing` (бисекция по сегментам), результат не зависит от FPS и содержимого кадров (`APPROVED_RULES.md`; тесты на 24/30/60/120 FPS).
- **Френк в V3 не интегрирован.** Его связь с физикой существует только в изолированной диагностике `track_diag/adapter.mjs` (его интегралы совпадают с `stateAt()` V3, ошибка 5,6e-17; повторено в `check.mjs`: 5,6e-17) и в предложении `plans/COORDINATE_CONTRACT_PROPOSAL.md` (ничего не внедрено): там START/STOP берут длительность и `velocityRamp` из метаданных клипа. Рабочий RACE_START: толчок на индексе 12 (gen3 f7), конец разгона индекс 43 (RUN #90) = 31 кадр = 1,2917 с (вариант N1). N3 (0,54 с) для проверки предпочтён, но как физика не утверждён.
- **Что зависит от клипа в физике (по контракту):** длительность разгона (прогресс и время START), положение начала RUN (`runStart`) и выравнивание следующего STOP по циклу RUN (`alignedStopTime`: `runStart + RUN_JOIN + k·0,5 с`).

## 3. Почему PREVIEW улучшенного стыка тоже 284 кадра
Совпадение построено, а не случайно: из хвоста убраны 2 кадра gen3 (f36, f37), а RUN-подводка удлинена ровно на 2 реальных кадра цикла (#88, #89 перед #90). Хвост A: вход 7 + gen3 36 + RUN 33; хвост B: 7 + 34 + 35. Проверка хэшей кадров: единственные подряд идентичные кадры в обоих preview — 9 кадров стойки (последний кадр события + 8 кадров удержания RACE_STAND, одинаково в A и B, заложено в сборке). Искусственного ожидания и дублирования нет. Первый кадр RUN #90 стоит на индексе 251 в обоих preview. Оговорка: в preview компенсация положения (Cp) для B считалась по связанному разгону в 29 кадров, поэтому сдвиги кадров различаются мелко (≤1 px) с индекса 228; для развязанной схемы массив нужно взять из `check_results.json` (ниже).

## 4. Минимальное изменение (если анимацию заменять независимо от физики)
Изменений кода V3 не требуется (для №4 ничего не меняется). Для Френка в метаданных клипа нужны два отдельных поля вместо одного:
1. `velocityRamp: {start: 12, end: 43}` — физика, остаётся как есть (31 кадр).
2. `visualJoin: 41` — индекс, с которого показывается RUN (#88); таблица кадров окна START: индексы 0–40 прежние, 41→RUN #88, 42→RUN #89, 43→RUN #90.
3. Массив смещения спрайта `shift` пересчитывается по тому же правилу, что для A (`per_frame_C_B_decoupled_*` в `check_results.json`): с развязкой компенсация доходит до нуля на индексе 43, а не 41 (в кадрах 41–42 она 16,1 и 8,1 исх. px).
Метрики спрайта (канвас, 1 px холста = 6,2 исх. px): при компенсации N1: шаг на стыке A −2,67, B −1,68; откат сглаженной позиции A 1,82, B 2,21. При производной компенсации N2 (как в принятом варианте): шаг A −2,66, **B −1,46**; откат A 1,03, **B 1,15** (критерий контракта ≤1 px: оба близки, у B на 0,12 px больше; дополнительный сдвиг до 13,3 против 10,9 исх. px). То есть выигрыш по стыку 1,2 px, потеря по откату 0,1 px.

### Необходимые регрессионные проверки
1. **Только кадры:** для одного набора seed (минимум 10 000 запросов, как `fallback_results.json`) сравнить с обоими вариантами клипа Френка `progress(t)`, `crossing`, места и `effectiveSeed`: должны совпасть бит-в-бит (после интеграции Френка в лабораторию).
2. **Dog4 без изменений:** `node validate.mjs`, `random_validate.mjs`, `fallback_validate.mjs`, `balance_audit.mjs 20261013 10000` — выходные JSON идентичны эталонам (хэши).
3. **Метаданные клипа:** `velocityRamp.end ≥ visualJoin`; кадр на `velocityRamp.end` = RUN #90; кадры 0–40 идентичны A; кадры 41–42 = #88, #89; цикл RUN #98→#87 непрерывен; следующий STOP стартует с #96.
4. **Спрайт:** откат сглаженной позиции ≤1 px холста (с N2 у B 1,15: или сохранить правило «≤1,2 px», или чуть усилить огибающую), шаг на стыке ≤ шага цикла (1,4 px), отсутствие скольжения опоры до отрыва.
5. **Визуально:** сравнение кадров idx 36–48 в крупном плане и в масштабе спрайта, 6 повторов, без двойных контуров.
6. **Детерминизм кадров:** один и тот же seed даёт те же индексы кадров (выбор кадра — чистая функция времени и таблицы).

## 5. Если синхронизация нарушится
Сохранить прежний игровой тайминг без потери качества движения — именно развязка выше: `velocityRamp` остаётся 31 кадр, RUN показывается на 2 кадра раньше внутри конца разгона. Скорость в этих двух кадрах уже 98,7–100 % от крейсерской, поэтому цикл RUN не противоречит физике. Если контракт потребует жёсткого «разгон = до стыка», оставить исходный f37→#90 или принять смещение Френка на −0,042 с за START отдельным решением с повторным аудитом баланса.

## Условия и ограничения
- Френк пока не подключён к V3; проверка выполнена на изолированных расчётах (формулы V3 прошли самотест), а не на живой гонке.
- Решение о контракте (длительность START из метаданных клипа) остаётся за пользователем и Codex; без него Френк в V3 не получает ни собственного START, ни этой оптимизации.
- Визуальная приёмка улучшенного стыка не пройдена.
