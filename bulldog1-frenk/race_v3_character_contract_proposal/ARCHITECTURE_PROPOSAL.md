## 0. Короткие ответы на семь вопросов

| # | Вопрос | Ответ |
|---|---|---|
| 1 | Можно ли оставить общую физику V3 с индивидуальными таймингами? | **Да**, если физические окна (START, RUN_JOIN, STOP, действия, BASE) остаются **общими константами**, а клип каждой собаки *вписывается* в окно визуальным скриптом (смещение начала, хвост в соседнее неподвижное окно, пауза в неподвижном окне, ограниченный retime). Физика не читает метаданные собаки. Это подход **P3** ниже. |
| 2 | Как не скользить, пока собака визуально стоит? | Спрайт стоит, пока не оттолкнулся (shift-массив гасит ход якоря: остаток 0,001 px/кадр), а сам клип **начинается раньше физического START на `lead` кадров** (для Френка 3), так что толчок попадает на более раннюю, более «медленную» часть кривой `u³−u⁴/2`: смещение якоря до толчка 0,9–1,5 px вместо 2,0–3,3 px. |
| 3 | Убрать несовпадение #93/#96 управлением фазой RUN, не двигая физический STOP? | **Да, одним параметром `lead = 3`** (визуальный START начинается на 3 кадра раньше физического). Сетка STOP V3 и период RUN (12 кадров) не трогаются; у принятого стыка `g3 f35 → RUN #88` кадр перед первым STOP становится #96, и так на каждом следующем слоте. Нужны 3 кадра паузы в неподвижном окне перед START (BASE или хвост действия) — они есть. |
| 4 | STOP и повторный START при разной длине клипов? | Алгебра окон (раздел 4.2): в **движущемся** окне кадры нельзя ни повторять, ни держать — только retime в заданных границах; **избыток** клипа уходит в соседнее **неподвижное** окно (хвост STOP → начало действия), **недобор** там же закрывается паузой в стойке. Не помещается → отклоняется на проверке ассета, не обрезается в игре. |
| 5 | Детерминизм, аналитический финиш, seed, сценарные ограничения? | Не затрагиваются **по построению**: визуальный слой — чистая функция `(персонаж, физические сегменты, t)`, ничего не пишет обратно. Подход с физикой «на персонажа» это **ломает** (измерено, раздел 3): при 10 000 seeds меняется победитель в 124–505 гонках и даже `effectiveSeed` в 2–12 гонках. |
| 6 | Ранние события, события перед финишем, анимация длиннее окна? | Все три разобраны на реальных гонках (раздел 6). Ключевые факты: 10,5 % собак имеют «ранний» первый ход (из BASE), минимальный зазор STOP → финиш 3,34 % трассы (39 px), минимальный RUN между START и STOP ровно 23 кадра. **Единственный найденный непомещающийся случай: Френк BUTTERFLY после STOP (−11 кадров), лечится retime ×1,093 или решением архитектора.** |
| 7 | Что менять в общей архитектуре, что — в метаданных? | Физику (`buildDog`, `scenario`, `crossing`) **менять не нужно**. Нужны: (а) вынести выбор кадра из `frameFor` Dog4 в чистый визуальный слой с перекрытием окон; (б) валидатор контракта; (в) явное правило «персонаж не входит в seed/физику». Всё остальное — метаданные (раздел 7). |

Что **не** принято автоматически: режим `native` из комплекта используется только как компонент (визуальный выезд за пределы окна) и только вместе с `lead`; per-character физический контракт (`velocityRamp`, `runJoin`) **отклоняется** на основе измерений.

## 1. Факты о V3, на которых стоит предложение

Из `dog4-v3-lab/model.mjs`:

* Физика собаки — цепочка сегментов `BASE → START → RUN → STOP → действие → START → … → RUN → FINISH_DECELERATE → BASE`. Длительности — **общие константы модуля** (`STOP=37/24`, `START=1`, `RUN_JOIN=23/24`, `LOOP=12/24`, действия `BUTTERFLY=121/24`, `ROLL=145/24`, `SNIFF`, `RETURN`).
* Кадры вычисляются отдельной функцией `frameFor(segment, time)` и используются только в `stateAt`. `buildDog`, `crossing`, `places` кадров не читают — результат гонки от клипов не зависит.
* **Но константы сидят глубже, чем «таймеры анимации»:** они входят в порог `early` (`START/2 + RUN_JOIN + STOP/2`), в сетку STOP (`runStart + RUN_JOIN + k·LOOP`), в проверку «событие не помещается» и, через `buildDog`, в перебор seed в `scenario.mjs` (`resolveRace` берёт первый допустимый seed). Любое отличие окна одной собаки меняет допустимость гонки.

**Цена события для собаки** (потерянное время относительно бега с крейсерской скоростью). START проходит `v·START/2`, STOP — `v·STOP/2`, действие — 0:

`cost = START/2 + STOP/2 + длительность действия`

| событие | V3 сейчас (общие константы) | Френк, «как снято» (START 31/24, STOP 73/24, SNIFF 8,333 с, BUTTERFLY 3,875 с) | разница |
|---|---|---|---|
| SNIFF_PEE+RETURN | 0,500 + 0,771 + 9,981 = **11,252 с** | 0,646 + 1,521 + 8,333 = 10,500 с | **−0,752 с (Френк быстрее)** |
| BUTTERFLY | 0,500 + 0,771 + 5,042 = **6,313 с** | 0,646 + 1,521 + 3,875 = 6,042 с | −0,271 с |
| начальный START | 0,500 с | 0,646 с | **+0,146 с (Френк медленнее)** |

Знак разницы зависит от клипа. Значит «собаки с длинными клипами проигрывают» — неверная модель; верная: **любая зависимость физики от клипа даёт смещение того или иного знака, причём по идентичности собаки**, а не по сценарию. Существующий `ANIMATION_CONTRACT.md` пишет «длительность действия измеряется у клипа, затем явно согласуется со сценарием»; предложение уточняет, *как*: клип подгоняется к окну сценария, а не окно к клипу (см. 9, решение D5).

## 2. Инварианты контракта

* **I1. Физическая независимость.** Всё, что определяет `crossing`, места, `effectiveSeed`, планы событий, — функция только общих констант, seed и *категорий скорости*. Метаданные персонажа в эти вычисления не входят.
* **I2. Нет выигрыша от длины клипа.** Для любых двух персонажей физические окна равны; «лишнее» время клипа тратится внутри окна.
* **I3. Нет скольжения.** Пока спрайт визуально стоит, мировая скорость спрайта (якорь + shift) ≤ 0,05 px/кадр. В фазах, где клип сам двигает корпус (RUN, торможение), скорость определяется клипом и не ухудшается относительно утверждённой V3.
* **I4. Нет скачков фазы.** На входе в STOP кадр RUN = требуемый кадр входа клипа STOP; на каждом стыке визуальный разрыв не хуже утверждённого (шаг ≤ 2,7 px, откат ≤ 1 px, «шероховатость» стыка не хуже принятой).
* **I5. Нет обрезки.** Каждый клип целиком помещается в доступный интервал; проверка статическая, на приёмке ассета, не в рантайме.
* **I6. Независимость от FPS.** Кадр и shift — чистые функции абсолютного времени `t`; никаких счётчиков кадров рендера в физике и в выборе кадра.
* **I7. Dog4 без регрессий.** Метаданные Dog4 = тождественное преобразование; golden-тест сравнивает со старым `frameFor`.
* **I8. Поводок.** Визуальное смещение от физического якоря ограничено (`|offset| ≤ 39 px` — это 3,34 % трассы, минимальный зазор STOP → финиш в 50 000 собаках), и в момент пересечения финиша оно равно 0 (пересечение всегда происходит в RUN, там shift затух).

## 3. Сравнение подходов

**P1. Физика на персонажа** (`velocityRamp`, `runJoin`, длительности STOP/действий — данные персонажа; вариант с «выравниванием стоимости события»).
**P2. Native-режим** (физика общая, клип играет 1:1 и «выезжает» за окно; фаза STOP не решена).
**P3. Общая физика + визуальный скрипт** (рекомендуется): P2 + `lead` + хвост/пауза/retime по алгебре окон + валидатор.

Измерения P1 на тех же 10 000 seeds (`fairness_sim/`, копия модели с переопределением констант для полосы 0; базовый выигрыш полосы 0 = 19,43 %; одни и те же seed для базы и варианта):

| вариант для полосы 0 | Δ выигрыш | Δ среднее время финиша | сменился победитель | сменился `effectiveSeed` |
|---|---|---|---|---|
| START 31/24 | −1,23 пп | +0,335 с | 189 | 5 |
| START 31/24 + `runJoin` 7/24 (контракт B комплекта) | −1,39 пп | +0,362 с | 167 | 2 |
| START 31/24 + STOP 73/24 | −4,20 пп | +1,231 с | 494 | 12 |
| SNIFF+RETURN 8,333 с | **+1,39 пп** | −0,518 с | 145 | 7 |
| START + STOP + SNIFF «как снято» | −3,13 пп | +0,718 с | 505 | 9 |
| P1 с выравниванием: START 31/24, каждое действие короче на 0,146 с | −0,42 пп | +0,127 с | **124** | **4** |
| **P3: любые клипы** | **0** (по построению) | **0** | **0** | **0** (физические входы те же; подтверждение — T1) |

Выводы по P1: (а) смещение в 1–4 пп и до 1,2 с — это не шум (тест обнаруживает сдвиги порядка 0,1–0,3 с); (б) оно бывает **в плюс и в минус** в зависимости от клипа; (в) выравнивание стоимости убирает среднее смещение, но **не убирает зависимость конкретной гонки от того, какая собака в какой полосе**: меняются победитель (124 гонки) и даже `effectiveSeed` (4 гонки) — запрос с одним seed даёт разные гонки при разном составе, что ломает воспроизводимость; остаточный +0,127 с — в основном начальный START, у которого нет действия для компенсации; (г) порог `early`, сетка STOP и проверки разделения становятся зависимыми от собаки.

| критерий | P1 | P2 | **P3** |
|---|---|---|---|
| Шансы не зависят от клипов | нет (измерено) | да | **да** |
| `effectiveSeed`/seed не зависят от состава | нет (измерено) | да | **да** |
| Решает #93/#96 без сдвига физического STOP | нет (двигает сетку STOP) | нет | **да (`lead`)** |
| Скольжение до толчка | зависит от кривой | якорь опережает до 3,3 px | **0,9–1,5 px, shift гасит остаток** |
| Помещается длинный клип (STOP 73) | меняет окно (смещение) | нет решения | **хвост в неподвижное окно** |
| Регресс Dog4 | возможен (общая сетка) | нет | нет (golden-тест) |
| Новый код | физика + сценарий + тесты 5 раскладок | визуальный | **визуальный слой + валидатор** |
| Главный риск | идентичность влияет на исход | сетка STOP, длинные клипы | перекрытие окон (хвост/lead) нужно проверять; клип, не вписывающийся ни в какое окно, возвращается на доработку |

**Рекомендация: P3.** Риски P3 — раздел 9.

## 4. Рекомендуемая схема P3

### 4.1 Слои

```
seed ─► planSeed/generateRace/buildDog ─► physical segments (общие константы)        [НЕ МЕНЯЕТСЯ]
                                              │ t, segments
                                              ▼
                    visualAt(character, segments, t) ─► {clip, frame, shiftX}      [НОВЫЙ чистый слой]
                                              ▲
              character-visual-contract (метаданные персонажа)
```

Физика ничего не импортирует из визуального слоя (проверяется графом импортов, T1). Персонаж → полоса назначается снаружи и не входит в seed.

### 4.2 Алгебра окон

Физические окна двух видов: **движущиеся** (START-разгон, RUN, STOP-торможение, FINISH_DECELERATE) и **неподвижные** (BASE, действие). Для каждого клипа персонажа:

| операция | где разрешена | условие |
|---|---|---|
| `retime` (скорость воспроизведения клипа по отрезкам) | везде | `rate ∈ [0,9; 1,12]`; кадры не дублируются «для подгонки», только пропускаются/повторяются равномерно |
| `pad` (держать позу стойки) | **только неподвижные** окна | поза из `holdPoses` персонажа |
| `tail` (клип продолжается после конца движущегося окна) | в **следующее неподвижное** окно | физическая скорость = 0, дрейф корпуса клипа ≤ поводок |
| `lead` (клип начинается раньше окна) | в **предыдущее неподвижное** окно | `lead ≤ releaseIdx` (толчок не раньше физического старта) |
| `shift` (смещение спрайта от якоря) | везде | закон «hold-then-decay» (комплект, N2 в 2 прохода), `|shift|` ≤ поводок, = 0 к стыку с RUN |

Условие вписывания (статическое, при приёмке):

* неподвижное окно: `tail + тело + pad + lead ≤ окно` для каждого вида действия и каждого пути (после STOP / «ранний» из BASE / финиш);
* движущееся окно: `тело ⊂ окно` после допустимого retime, либо избыток уходит в `tail`.

Нарушение → вердикт `NO_FIT`, ассет возвращается на доработку. Нигде нет усечения в рантайме.

### 4.3 Схема данных (v1, предложение)

Полный пример — `frenk_visual_contract.example.json`.

```ts
type CharacterVisualContract = {
  schema: 'character-visual-contract/v1'; character: string; fps: 24;
  canonicalAsserted: { START_s; STOP_s; RUN_JOIN_s; LOOP_s; ACTION_s: Record<Kind,number>; BASE_FINISH_s }; // утверждение, валидатор сверяет с model.mjs
  run: { cycle: {firstSrc; lastSrc; frames; periodMustEqual_s: 0.5};                                     // период RUN обязан = LOOP
         stopEntry: { previousRunFrame: number } };
  START: { tableRef; keys: {releaseIdx; visualJoinFirstRunIdx; runFrameAtJoin};
           lead: { frames; derived: true; max }; retime: null | Segment[]; shift: { law; arrays?; perCategory: true } };
  STOP:  { keys: {movingFrames; settledFromFrame; bakedRootTravelCanvasPx};
           plan: { inWindow: [a,b]; tail?: { frames: [a,b]; overlay: 'action.head' | 'BASE_FINISH'; requires: 'speed==0' } }; rateBounds };
  FINISH_DECELERATE: { plan };
  ACTIONS: Record<Kind, { bodyFrames; source; pad: 'stand' } | null>;
  limits: { retimeRateBounds; maxPrePushOffsetCanvasPx; smoothedRollbackCanvasPx; joinStepCanvasPxAbs; maxVisualForwardOffsetCanvasPx };
};
```

Как это ложится на то, что уже есть у Dog4: Dog4 = `lead 0`, `retime null`, `tail` нет, `shift 0`, таблицы кадров из текущего `frameFor` (`variableFrame` 72+24 fps для START — это уже поддержанный в V3 вид retime). Метаданные Dog4 восстанавливают существующее поведение 1:1 (T2).

### 4.4 Формулы

* **`lead`** — наименьшее `d ≥ 0`, при котором кадр RUN в физическом кадре `первый STOP − 1` равен `stopEntry.previousRunFrame`. Для визуального индекса `visualIdx = физический кадр + lead`. Период RUN = LOOP (12 кадров) ⇒ тот же кадр перед **каждым** слотом сетки (проверено на 12 слотах).
* **Смещение якоря до толчка** (START-кривая V3 `v·(τ³ − τ⁴/2)`, `v = 1170 px / 42 с × категория`): `drift(τ) = v·(τ³ − τ⁴/2)`, толчок при `τ = (releaseIdx − lead)/24`.
* **Поводок:** `|x_sprite − x_anchor| ≤ 39 px`; пересечение финиша судится по якорю, shift затухает до пересечения.

### 4.5 Временные диаграммы (физические кадры, 24 к/с; 0 = начало физического START)

**А. Старт гонки, Френк, `lead = 3` (visual idx = физ. кадр + 3)**

```
физ. кадр: -12        -3  0               9            24                      38  ...  46 47        59
физика:    [BASE 12 кадров ]|[START 24 кадра, v: 0→крейсер]|[RUN ........................................
                             ^первый STOP V3 = 24+23 = кадр 47 ──────────────────────────┘ (сетка +12)
визуал:           idx0 ─ приседание (RACE_STAND-совместимое) ─ толчок idx12 ─ галоп gen3 ─ idx41 = RUN #88
                  ↑ начало на 3 кадра раньше   ↑ τ=0,375 с   ↑ конец физ. START = idx27    #88…#96 (9 кадров)│STOP f1
RUN-кадр перед STOP: #96 (требуется #96) ✓ ; без lead было бы #93 (рассинхрон 3)
```

**Б. Событие после STOP (неподвижное окно действия), Френк SNIFF_PEE**

```
физика:    [STOP 37 кадров, v→0 ][ окно действия SNIFF+RETURN = 239,55 кадра, p = const ......][START ...
визуал:    [STOP f1..f37 1:1    ][STOP f38..f73 (хвост 36)][EVENT 200 кадров         ][lead 3]
                                                                                       сумма 36+200+3 = 239  ≤ 239,55 ✓ (запас 0,55 кадра)
```
`BUTTERFLY` (окно 121 кадр): 36 + 93 + 3 = **132 > 121** (−11): нужен retime ×1,093 по хвосту+телу либо иное решение (раздел 9, D3).

**В. «Ранний» первый ход (10,5 % собак): действие прямо из BASE**

```
физика:    [BASE 12 к][ окно действия ...............................][START ...
визуал:    [стойка   ][EVENT 200  ][пауза 36,55 кадра][lead 3]     (хвоста STOP нет: собака не двигалась)
```

**Г. Финиш**

```
физика:  ... RUN (пересечение финиша всегда в RUN) ... → первый слот сетки после пересечения → [FINISH_DECELERATE 37 к][BASE 36 к]
визуал:                                                  STOP f1..f37 1:1 ─────────────────────► [STOP f38..f73 = хвост 36] → стойка
Окно 37+36 = 73 кадра = клип STOP Френка 73 кадра: запас 0 — вписывается точно.
```

## 5. Подробные ответы на 7 вопросов

**1. Общая физика + индивидуальные тайминги.** Физические константы — единственный «источник времени». Индивидуальные тайминги живут как *вписывание клипа в окно* (4.2). Условие: клип должен *помещаться* в окно по алгебре; иначе ассет дорабатывается или архитекторы осознанно меняют общие константы **для всех** (D4). Выигрыша от длины клипа нет, потому что длина клипа в расчёт гонки не входит (I1/I2); измерение P3 — нулевое смещение по построению, проверка T1 подтверждает бит-в-бит.

**2. Начало движения против фактического толчка.** Физическое ускорение V3 стартует плавно: к моменту толчка при `lead 3` скорость якоря 31,6 % крейсерской, пройдено 0,9–1,5 px (NORMAL 1,19 px). Спрайт в этот интервал стоит: shift-массив компенсирует ход якоря (`engineMinusShiftResidualStep = 0,001 px/кадр`, `slip_check_results.json`), без компенсации якорь двигался бы на 0,20–0,34 px/кадр (при `lead 0` — 0,35–0,59). После толчка спрайт догоняет якорь (откат сглаженного положения 0,03–0,73 px, шаг на стыке −1,38…−1,56 px — в пределах критериев комплекта, `shift_arrays_lead3.json`). Чем раньше толчок относительно физики (больше `lead`), тем меньше смещение, но `lead` ограничен фазой RUN (3) и толчок не должен быть раньше физического START (`lead ≤ 12`).
*Честно:* скольжение лап **внутри** клипа (baked-движение корпуса gen3/STOP) контрактом не устраняется. В сборке START шов V1 f16 → gen3 f2 даёт собственный шаг корпуса 1,83 px/кадр (сидит в клипе, не зависит от `lead`) — отмечено, не исправлялось. Скольжение лап в STOP и в RUN вне критерия I3 надо мерить отдельно (T6, `paw_tracking.json` покрывает только START).

**3. #93 против #96.** Три рычага, только первый не трогает ни физику, ни выбор стыка:

| рычаг | что | цена |
|---|---|---|
| **L1. `lead 3`** (рекомендуется) | клип START стартует на 3 кадра раньше физического; принятый стык `f35→#88` и физика не меняются; RUN #96 перед первым STOP | 3 кадра паузы в стойке перед START (есть в BASE и в хвосте действия); пересчёт shift-массивов (сделано, `shift_arrays_lead3.json`) |
| L2. Выбор другого стыка под нужную фазу | при `lead 0` фаза-допустимые пары: `f31→#87` (шероховатость 24,5), `f36→#92` (25,7), `f40→#96` (27,1) против принятых 18,3 и исходных 30,2 | хуже принятого стыка, **новое визуальное решение** |
| L3. Retime галопа gen3 | сжать 29→26 кадров (×1,115), стык `f35→#88` тот же | видимое ускорение галопа; требует пересчёта и глазной проверки |
| L4. Rate-slew внутри RUN | нужно +3 кадра за 6 доступных = ×1,6 | не годится (и «адаптивный RUN» уже отвергнут V3) |

Таблица «лучший стык при каждом `lead`» (`contract_check_results.json → bestJoinPairByLead`) показывает, что `lead` — это ещё и параметр оптимизации: `lead 1 → f36→#91` (16,5 — лучший из всех пар, смещение до толчка 2,07 px), `lead 2 → f36→#90` (17,3), `lead 3 → f35→#88` (18,3, **принятый**, 1,19 px). Рекомендуется `lead 3` с уже принятым стыком; `lead 1` — вариант на глазную оценку (новый стык не рендерился). Изменение физического `runJoin` (контракт B) — **отклонено**: оно двигает сетку STOP и порог `early` для одной собаки.

**4. STOP и повторный START при разных клипах.** Правила 4.2 плюс факт про Френка: движение клипа STOP длится до кадра 63 (дальше корпус неподвижен, `frames_meta.json`), то есть **не 37**; сжать в окно ×1,7 неестественно. Поэтому первые 37 кадров играют 1:1 в физическом окне торможения, остальные 36 — хвост в неподвижное окно (дрейф корпуса клипа в хвосте 10,6 px, в окне 6,4 px, всего запечено 17,0 px; поводок 39 px). Совпадение 37+36 = 73 даёт точную посадку в FINISH_DECELERATE+BASE. Повторный START: `lead` занимает последние `d` кадров окна действия (или BASE у начального старта); бюджет окна считается с ним (диаграмма Б).

**5. Детерминизм и ограничения.** Новых вызовов RNG нет; seed и порядок `random()` не меняются; планы событий, 25 %-интервалы, 8 %-разделение, «не все пять стоят», пороги `early` и `cannot fit` вычисляются из общих констант — одинаковы при любом составе. Аналитический `crossing` — тот же код. FPS: кадр и shift вычисляются из абсолютного `t` (формула `floor(t·24 + lead + ε)`), физика от рендера не зависит.

## 7. Что менять в общей архитектуре и что — в метаданных

**Нужно в общей архитектуре (небольшое, не физика):**

## 9. Риски, ограничения, решения для приёмки

**Ограничения этого анализа (честно):**
* Визуально ничего не рендерилось и не оценивалось глазами; все утверждения о плавности — по расчётным метрикам комплекта.
* Содержимое `EVENT` SNIFF_PEE V3.2 (200 кадров) принято как цельное тело; есть ли в нём собственные паузы в начале/конце, не проверялось — это определит реальный запас 0,55 кадра.
* Shift-закон для хвоста STOP и пересчёт после `lead` сделаны только для START; для STOP/хвоста (`bakedRootTravel` 17 px, сдвиг стойки −125 px) массивы не строились.
* Симуляция P1 — копия модели с переопределением констант для одной полосы; «STOP 73/24» там — верхняя оценка, а не реальный контракт.
* ROLL Френка отсутствует; вердикт для него не выдаётся.
* Дрейф корпуса «запечён» в клипе (+17 px в STOP, шов V1→gen3 1,83 px/кадр) — свойство клипа.

**Риски P3:**
| риск | серьёзность | смягчение |
|---|---|---|
| запас окна у SNIFF 0,55 кадра (SNIFF) / 0 (финиш) | средняя | валидатор с точностью до кадра; при изменении клипа пересчёт |
| BUTTERFLY не помещается без retime ×1,093 | средняя | D3 |
| длинные паузы в стойке (до ~1,5 с) выглядят «мёртво» | низкая/средняя | паузы только в неподвижных окнах; живая пауза — отдельное решение, новых клипов нет |
| `lead` занимает конец окна действия | низкая | входит в бюджет вписывания |
| перекрытие окон усложняет визуальный слой | средняя | один чистый модуль + golden-тест Dog4 |
| сетка STOP зафиксирована периодом RUN 12 кадров | низкая | период — обязательное поле валидатора |

**Решения, которых жду от архитектора:**
* **D1.** Принять P3 (общие физические окна + визуальный скрипт) и отклонить P1 (per-character физика)?
* **D2.** `lead 3` с принятым стыком `f35→#88` (рекомендуется) или оценить глазами `lead 1` со стыком `f36→#91` (лучше по метрике, новый стык)?
* **D3.** BUTTERFLY Френка: принять retime ×1,093 после проверки глазом, либо иное (например, поднять общее окно BUTTERFLY для всех — это меняет Dog4 и требует его переутверждения)?
* **D4.** Допустим ли пересмотр общих окон для всех собак (как отдельная архитектурная задача)? Для этого предложения не требуется.
* **D5.** Уточнить `ANIMATION_CONTRACT.md`: «длительность согласуется со сценарием» = клип вписывается в окно сценария, а не наоборот.
